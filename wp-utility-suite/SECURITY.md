# Security design

WPUS trusts the WordPress runtime, installed PHP code, host configuration and the site's primary database. The browser, remote clients and public request fields are outside that boundary. Sites use separate tables derived from the active WordPress site. Use HTTPS in deployment.

- **Identity and permissions.** WordPress owns authentication. Admin writes require POST, the operation's capability and its WordPress nonce. Settings toggles also require the module-management capability. A health probe can use a dedicated HTTPS WordPress Application Password with only the health capability and the core read capability. A background operation can act only on the recorded site, object and operation. Content expiry rechecks the initiating user's membership and object capability.
- **Integrity.** WordPress provides database credentials. Revisioned changes to settings, notes and redirect rules use conditional writes in the same InnoDB transaction as the audit record. Schema changes run under a database advisory lock and remain gated until verification. Public 404 recording uses bounded aggregates. Lifecycle removal affects plugin-owned state and defaults to retention.
- **Data handling.** Audit rows store allowlisted metadata and WordPress identifiers. No IP address, raw public URL, query string or credential is collected. Notes are bounded plain text for technical use. WordPress privacy tools export attributable records and redact author and actor identifiers. Maintenance deletes expired operational rows in bounded batches. Backups can retain copies and need the site's access controls and retention policy.
- **Ingestion.** Admin forms use bounded scalar fields and explicit validation. Table names are derived from trusted WordPress configuration and fixed suffixes. Output is escaped for its context. Redirect rules use a conservative same-site path grammar, reject chains and use WordPress's safe redirect API.
- **Outbound traffic.** Outbound features start off and are subject to an operator stop. Remote endpoints require HTTPS, public DNS results, connection pinning, explicit host approval and bounded requests. Keep secrets out of WordPress settings and diagnostics.
- **Abuse cases.** Test stale revisions, missing nonces, unauthorized direct URLs, multisite ID overlap, stored markup, redirect loops, revoked expiry permissions and exhausted 404 budgets. Treat a changed post as a skip. A core write from another plugin can still race the final post update.

## Order erasure and notes pagination

WooCommerce decides when an order has been anonymized. PressUtils uses the current site's WooCommerce CRUD API to check the order at capture and before sending. The site-local outbox stores only the order ID as its cancellation reference. The encrypted body contains the order ID and status codes. It carries no billing email, address or payment details. When WooCommerce anonymizes an order, PressUtils cancels its retained bodies and clears its linkage and source marker. The migration cancels old order bodies that have no cancellation reference. Requests already sent and data stored by a receiver follow that receiver's privacy process.

If the immediate transaction fails, retain a site-local retry marker with the order ID and no order fields. Only the WooCommerce anonymization hook creates this marker. The scheduled CRM sweep retries a bounded batch even while outbound delivery is paused. Each retry shares the capture lock and removes the marker in the same transaction that clears delivery data and linkage. The existing send-time checks remain in force. If the database also rejects the retry write, record a generic audit event and let the existing expiration policy bound retention. A scheduler failure can delay retries, so the operator should monitor scheduler health.

The release verification receiver accepts only synthetic events. It verifies signatures over the raw request, checks freshness and deduplicates the delivery ID before recording an acceptance. Its temporary key and database stay inside the fixture. Test workflows use read-only repository access. The dedicated tagged build uses a separate job with the permissions required to attest the ZIP and SBOM, and a maintainer publishes the verified assets.

The notes collection checks each linked post with WordPress's edit permission before choosing any cursor that will be returned. The scan is bounded so a delegated request cannot walk an arbitrarily large store. The caller receives cursors derived from visible notes.
